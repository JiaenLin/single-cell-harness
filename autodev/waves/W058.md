# W058 (PROF): every isolated plugin group has a lock for the platform it is installed on, and is built there

**Registered** 2026-11-12 by the coordinator, before any change. ROUTE item R31 (GAP-C88), moved ahead of the rest of
the plugin line by the direction review of 2026-11-12 (R24's own row says it waits for R31; W055 ran first, and its
dev-suite job cannot pass for a plugin whose environment is not built where the suite runs). **Goals** A4.1, PROF.1.
**Repository** scProfile, branch `autodev/W058-group-locks`, stacked on W055's head `55a60d5` (W055 added a check of
each plugin's pin against its lock; the two merge as one batch). No design step: the facts are the installer's and
the cluster's, and a preflight finds them (direction review, section 2).

## Why
An isolated plugin group (one that cannot share the main environment: an R toolchain, a conflicting pin) has no lock
for the cluster's platform, and its lock state is stale against the shipped lock, so `install` refuses there. The
cluster's dev suite grades each plugin on its BUILT environment and accepts no refusal (W055), so no plugin of an
isolated group can pass it, and A4.1 cannot count them.

## THE CLASS
Every pair (plugin group the tool declares, platform the tool says it installs on) has a lock that is fresh against the
group's own declaration and that builds. The ONE place that defines the set: the tool's declaration of its groups and
of its platforms (the builder names the file and lines; if the platforms are stated nowhere, stating them there is
change 1). The ONE test that walks the set from that place: for each pair, a lock exists, its recorded inputs equal the
group's declaration today, and every exact pin a plugin of that group declares (W055's source stage) is the version the
lock holds; a new group or platform needs no new test. Outside, as counted limits: platforms the tool does not declare.

## THE SIZE (three changes)
1. The locks, written by the tool's own lock verb for every pair of the set (never by hand), and the walking test.
2. `install` on a platform with a missing or stale lock refuses naming the group, the platform and the command that
   writes the lock (it refuses today: the words are checked, and made true if they are not).
3. ONE cluster job, written and not submitted: it builds each isolated group's environment from its lock under the
   prefix the dev suite reads, and runs the tool's `selftest` for each; it honours `CHECK_ONLY=1` (everything before
   the first build, then `PREFLIGHT: OK` or `PREFLIGHT: MISSED (n)`); its prediction is written before any run.

## Acceptance check
- The walking test passes, and fails when one lock is removed, when one is made stale, and when a plugin's pin is
  moved off its lock (each for its own reason).
- On the workstation: a dry run of `install` for each pair resolves from the lock alone; a missing lock is refused by
  name.
- The job reads AS PREDICTED: each group built, each `selftest` ok; then W055's dev-suite job can be graded on the
  built environments.
- A PROOF TABLE in this file: one row per judge the wave adds (the walking test, each refusal, each graded line).

## Prediction
A4.1 does not move by this wave alone; it lets the dev-suite job count the plugins of isolated groups (the first:
the one already converted). GAP-C88 closes on the job.
