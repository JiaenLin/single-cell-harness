# W059 (HARN): the cohort-run skill, and a cold agent's trial on the second cohort

**Registered** 2026-11-12 by the coordinator. ROUTE item R07 (GAP-003), with R14, R21 and R35 folded into its trial by
the direction review of 2026-11-12 (one chained run of the second cohort is both the cohort's missing stages and the

driver (W056) is merged. **Design first** (RULES item 21a): a Fable agent writes the section "Design" below before any
builder starts; the builder builds that design; the trial is the wave's verification.

## Why
GOALS A7.1: an agent with no prior context drives a cohort through the family with the skill alone: assemble, submit,
recover, audit, record. Nothing of it exists; the driver that makes it possible (one request, four stages, a generated
job) is in its last fix round. The sufficiency check found that without ONE planted failure, declared before the trial
starts, the "recover" act cannot be shown and the test stops at 4 of 5.

## The question the design must answer
What is "recover", as a CLOSED list: which failures the skill must tell apart (a pins miss, an absent input, a tool's
refusal, a kill at the time limit, a prediction that missed, and whatever else the driver's own verbs can report), the
ONE act allowed for each, and the rule that the request is the only thing the agent may change (never a tool, a job
file, a record or a threshold). And: through which command a cold agent submits and watches, given that compute runs
only inside submitted jobs and the agent must not need this program's private machinery. Answered wrongly, the skill
retries blindly, or meets a planted failure it cannot classify.

## What the design carries (item 21a)
The problem from the root; the design by construction (THE CLASS: the closed set of states a run can be in, the one
place that defines it, the one test that walks it); one other design and what it gives up; the steps as at most three
changes a wave (so: how many waves); the trial's protocol (what the cold agent is given, the planted failure and how
it is declared beforehand, what is graded for each of the five acts, who grades); the attacks the builder must run;
what the design gives up.

### 1. The problem from the root
**A cold agent has** `sch plan --request` and `sch run --request` with `--out` or `--job` (cli.py:128-150, 280-315): a schema whose refusals name their field
(drive.py:46-66, 558-1080), a generated job that pins its inputs, seals its folder and ends in one `GATE:` line (1750-1947), and a driver that refuses by name a
late answer (1230-1247) and a changed record (1315-1320, 1374-1377), as W056's verifier re-ran. **It lacks** (a) a way to submit: the generator ends "nothing
was run: the coordinator submits it by its recipe" (cli.py:291-292), and the recipe is run by this program's private gate (`setup/autodev/gate.py`); (b) a
reading of how a run ended, which is spread over four writers: the job's seal and `VERDICT` lines (drive.py:1865-1944), `DRIVE.json`'s status and free-text
reason (1400, 1505-1516), the kernel's status of the stage's mount (kernel.py:552-643), the scheduler's word (executor.py:303-401); (c) who may answer a user's
question (the plan only prints them, drive.py:1090-1093, 1116-1121); (d) a record that is not its own prose.
**Why prose cannot pass a planted failure.** "If it fails, look at the log" asks the agent to classify from sentences, and its two cheap acts, retry and edit,
are wrong for most ends: 20 of the 31 below stop. A planted failure is a state where a retry fails again. Prose cannot be walked by a test, and a grader reads
only the agent's account. So classification is the harness's code, and the agent's part is one act a state. **One fact shapes recovery.** Each submission makes
a new run folder, read-only at the job's end (drive.py:1851-1853, 1882), so a job cannot resume: each recovery is a new run from stage 1 (inf.).

### 3. The design by construction
**What the skill is.** `skills/cohort-run/` in the harness. Documents: `SKILL.md` (at most 120 lines: the loop, the never-list, where each given thing lies; no
state table, no site fact) and `SITE.md` (what a site directory must hold, names only: `stack.yml` and `job.yml` as the driver reads them, drive.py:81-85,
1686-1703; a new `tools.yml` naming where each tool is installed; the site's own rules document). Commands, all in `sch` and held by its suite: `sch drive` with
`next`, `submit`, `audit`, `record` and `states`; and `check.sh` (three lines calling `sch drive audit "$1"`: every job's `--check`). The agent writes ONE file,
`request.yml`. The user's answers are a given file, `decisions.yml` (`by:` one name; `answers:` name to value), which the agent never writes.
**The loop is the whole procedure.** Run `sch drive next --request request.yml --decisions decisions.yml`; it prints `STATE: <id> [<stage>]`,
`EVIDENCE: <file>: <the line or field matched>` and `ACT: <one act>`; do that act with the command it names; repeat until `DONE` or `STOP`. `next` reads only
files and the scheduler, needs no git, and writes one row of `ATTEMPTS.tsv` for each SET, RESUBMIT or ASK it prints. Each of the five acts ends in a line a
command printed: `STATE: ready` (the plan holds; no question that stops a run is open, drive.py:1092, 1119); `SUBMITTED: attempt <n> job <md5> run <folder>`;
the STATE and ACT rows; `AUDIT: HOLDS (n)`; `RECORDED: <sha256>`. Section 6's table says what a grader reads for each.
**Submit and watch, for a cold agent.** `sch drive submit` is generation and submission in one call, so no job is edited between them. It (i) refuses unless the
request equals the last attempt's sealed `request.json` (drive.py:1463, 1882) with exactly the SET rows since applied (parsed, not bytes), and the sheet hashes
as recorded or holds the names an ASK row asked; (ii) generates the job by `write_job` (1950; a new number, it refuses to overwrite: 1953) with the sheet's
answers and name as `--answer` and `--by`, `--tool` for each stage's checkout read where the command runs, `--predict` the text of `sch drive audit --predict`
and `--check` the skill's `check.sh`; (iii) refuses a job with no prediction or with a pinned input absent (1812); (iv) runs the job's own recipe, the lines
between `# SUBMIT-BEGIN` and `# SUBMIT-END` (1845-1854), each check line fatal: step 4 of `gate.py submit` without the program's mirror, watch row, RUNLOG or
checkout moves; (v) appends the attempt to `ATTEMPTS.tsv`, each row holding the sha256 of the row before. Git is used only by the recipe, on the login node
(1850); a compute node has none. Watching is `next --wait MINUTES`, through the executor's own commands and timeouts (executor.py:193, 303-325).
**Audit** grades what holds for any cohort, a `VERDICT` line each: each seal is the one `INPUTS.json` names and what it handed on hashes as sealed
(drive.py:1368-1396, 1641-1643); decisions, who gave them and each tool's params equal each seal's (1259-1270); the run's files are as recorded (1328-1340); on
single cells no param performs an upstream step and no `upstream.<step>` answer exists but the sheet's (640-659). `--predict` prints them before any run.
**Record** is generated from the run folders and `ATTEMPTS.tsv`, with no clock: every attempt with its state and act, the job header's hashes (1829-1833), each
answer with who gave it, each stage's tool, version and `cannot_show` (1096, 987), the verdict and audit lines. **What the skill assumes of a site (5):** a
scheduler with `qsub`, `qstat`, `qdel` (drive.py:1700; executor.py:193); a site directory as `SITE.md` says, named by `$SCH_SITE`, owned by the site, in no
repository of the family (never this program's `autodev/.machinery`); a login node where the scheduler's commands and reading a cohort's inputs are allowed, and
nothing else; the cohort's folder at the site; a scheduler that keeps a finished job's record until the next `next` (else rows 15, 22, 23 read as 16, 24).

### 4. One other design, and what it gives up
**Recovery inside the driver:** the generated job classifies its own end, raises its own size and resubmits itself; the skill is a README. It gives fewer round
trips and a resume from the failed stage. It gives up the pre-declared job (a job that rewrites its sizes is no longer the file whose md5 and prediction were
recorded before it ran: rule 1c), a stop outside any job for the user's questions, and an act to score (A7.1 would measure the driver). Not chosen; its sound
half is kept: recognition IS inside the harness (the table, the ids in `DRIVE.json`), held by the driver's suite, and only the act is the agent's.

### 6. The trial's protocol
**Given, exactly three folders,** each file's sha256 recorded first. (1) The skill: the harness checkout at the site, at the merged commit. (2) The second
cohort: its delivery as delivered, and its design (the design sheet; the assay, species and tissue; what ran upstream, by tool and release; the analyses asked;
the annotation tree to use, marked a draft; `decisions.yml`), written by the coordinator from the cohort's own records by the pre-decider's rules. (3) The
trial's site directory, and a shell where the site's document says commands run. **Not given:** `autodev/`; any earlier run, request, job, log or promoted
result of either cohort; any memory file; this program's skills for the site; word that a failure is planted. The brief is one sentence: run this cohort through
the family with the cohort-run skill, and stop at DONE or STOP. **Model and tools:** a fresh agent on the model the program builds with (which model a cold
trial may run on is not ruled: direction review, section 5); a shell, Read, Write, Edit; no sub-agent, no web; at most 150 calls a session. Sessions may be
several, each cold again: the skill's only state is `ATTEMPTS.tsv` and the run folders.
**The ONE planted failure: row 22, stage 1 killed at its time limit.** One line added to the trial's site `stack.yml`:
`pbs.plugins.<the stage-1 plugin>.walltime: V`. The executor lays `pbs.plugins.<name>` over the site's block for that run (executor.py:604-609), layers merge
key by key (`sch/stack/compose.py:5-6`), and a request's own size for a stage is laid over the site's (drive.py:1592-1595): with no size for stage 1 in the
request its job asks V, and after the act 2V (inf.; build 1 shows it). V is 0.7 x the wall time the scheduler recorded for that tool's own job on this cohort's
stage 1 at the commit to be run: attempt 1 dies after V, attempt 2 fits in 2V with 40 % to spare, and a retry fails again. Cost: V and a queue wait. **Declared
first.** Before the agent starts the coordinator writes `PLANT.md`, out of its reach: the row; the line added; V and the record it came from; the expected
`STATE:` and `ACT:` lines word for word; the hashes of the given files, both site files and a listing of the cohort's promoted results; the cohort's own
prediction; the grader's command list. Only its sha256 goes into the ledger row that registers the trial, committed by `setup/autodev/commit.sh` (its COMMITTED
line); after the last attempt the note is committed whole, and a note that does not hash to that value voids the trial. **The grade** is the coordinator running
the note's command list on files commands wrote and the scheduler's record, never on the agent's prose; the next audit pass re-reads the row.

### 7. The attacks before hand-back, and what the design gives up
**Attacks.** ATTACKS 12: for every row the WRONG folder must not print that row; a `FAILED.txt` holding `exit=0`, a `SEALED.txt` beside a failed `DRIVE.json`
and a `DRIVE.json` cut mid-write each print `unknown`. ATTACKS 33: `next`, `audit` and `record` with no git on PATH, and with a tool's checkout absent or at
another commit: a correct run must not read a miss. ATTACKS 47: each command from another working directory, and `check.sh` from the job's directory on a
correct-looking fake run: every line HELD. Also: a run folder copied elsewhere never reads `as-predicted`; a killed job the scheduler is silent about reads
`stage-lost`, never over-walltime; a crash one second under the limit reads `stage-crashed`; a SET past the largest queue is a STOP; an answer added to the
sheet with no ASK row is refused; the leak scanner finds nothing in the skill, the table and the tests under both cohorts' terms.
**Measured first.** By the coordinator's short jobs, before build 1: a real kill at a time limit and at a memory limit through the executor (the job's own
`exit=`, the scheduler's exit word, used against asked, and whether `facts.json` then holds `cost.wall_s`: rows 15, 22, 23 rest on it). By the builder, on the
merged head: whether a job generated with no `--predict` can print `GATE: AS PREDICTED` (drive.py:1789 says it cannot; 1876 lets it, inf.); what becomes of a
stage's job when the driver's own job is killed; the role names `run_inputs` gives (drive.py:339-417, unread here; rows 8, 9 rest on them); the pins check and
recipe as the fix round leaves them. **What the design gives up.** (1) Every recovery restarts at stage 1: a late failure costs the whole chain; a resume
