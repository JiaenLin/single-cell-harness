## What was measured
The first cohort's real joint object (about 3.2 GB, written by the integration tool at its `main` through the harness)
converts with the lab's documented command, no flag and no manual step, and the bundle equals the object in every
value compared; the Studio opens it with no page error. That half of A6.2 is YES. But on this real object the live
pair tells a user things that are FALSE, and the run is not shown:
1. **The integration method is guessed from a name.** The Studio says "Batch integration: harmony" and its Methods text
   says the data were "corrected with harmony, as recorded in the object", with that method's citation. The object
   records another method, and the embedding that opens is that other method's. The lab decides "harmony" when any
   embedding's name holds the word. A user can paste a false methods sentence into a paper.
2. **Raw counts are dropped without a word.** The object holds a counts layer; for an object large enough to be split
   into parts the lab leaves the counts out with no note; the Studio then says "Raw counts: not found", disables the
   pseudobulk export, and elsewhere still says the pseudobulk counts can be saved.
3. **"Total counts" is not counts.** The per-cell QC total is summed from the log-normalised matrix and drawn under the
   label "Total counts".
4. **The lab's own page promises what does not happen** before converting ("Pseudobulk DESeq2: yes", "All 11 travel
   in the file" where 5 travel), and a count of grey cells includes cells with no coordinates.
5. **The run is not shown.** The card lists the producing tool's record by tool, version and commit (each true); the
   job is recorded as a group and is not carried, and no run key, stage, date or input is recorded as a field. A user
   can tell which code made the object and not which run. (This is the test's second half: PARTLY.)

## The question the design must answer
Which facts about an object may the lab STATE, and where must each come from: a fact the object records (then it is
read from a named place, and "as recorded in the object" is true), a fact the lab measures from the values (then it
is said as measured, with how), or a fact nobody recorded (then it is said as not recorded, and never guessed from a
name). And for the run: which writer records the run's identity (a run key, a stage, a job, a date) as fields the
lab's closed reader already carries, so that the second half of A6.2 becomes YES without the lab reading anything new.
Answered wrongly, the next real object brings the next false sentence.

## What the design carries (item 21a)
The problem from the root; THE CLASS (every statement the lab or the Studio makes about an object: the closed list,
each with its source kind: recorded, measured, not recorded; the one place that defines it; the one test that walks
it); the design by construction; one other design and what it gives up; the build as waves of at most three numbered
changes each, per repository, in order, with each wave's acceptance check and the rows its proof table must hold
(the real object's shapes rebuilt as SYNTHETIC fixtures: no cohort value in any repository); what moves A6.2 to 2 of 2
and by which run; the attacks the builders must run; what the design gives up.
