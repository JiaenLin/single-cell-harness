# W063 (ALL): cold reproductions of sealed stage runs, from the record and the docs alone

**Registered** 2026-11-12 by the coordinator. ROUTE item R11, moved up by the direction review of 2026-11-12 (A2.3 is the
lowest test: 0 of 4, never attempted; each reproduction is 0.25 and two reach the bar). **Goals** A2.3, and A2.2 through
what each attempt finds false in the docs. **No tool is changed by this wave.** The direction review said no design was
needed; setting the first one up showed a PROTOCOL is: what the record is, what a cold agent may hold, which commit it
runs, what counts as reproduced. A Fable design agent writes the section "Design" below (D9) before any attempt.

## Why
GOALS A2.3: an agent with no prior context reproduces a sealed stage run from its record and the docs alone. The score
is the number of sealed stage runs so reproduced, of 4. Nobody has tried. A reproduction that passes only because the
agent was handed this program's own notes, jobs or machinery proves nothing; one that is graded after the fact by
whoever wants it to pass proves nothing either.

## The question the design must answer
What exactly is handed to the cold agent (the RECORD of one sealed run: which files of its folder, and nothing of the
project's history; the DOCS: the tool's repository at the record's commit, and the site's own notes for writing a job),
what it may do (write one job and its prediction; never touch the cluster; never see an earlier job for that stage),
which commit of the tool it must run and where the record says so, what "reproduced" means for each stage (which
outputs, compared how, with which stated tolerance for a stochastic step) fixed BEFORE the attempt, who submits and who
grades, and which four runs, in which order, at what cluster cost.

## What the design carries (item 21a)
THE CLASS (the closed list of what a cold agent may be given, and the one check that proves it was given nothing else);
the protocol by construction; one other protocol and what it gives up; the four runs with each one's record, commit,
comparison and cost; the proof that a grade cannot be fitted afterwards; what each attempt hands back (every doc line
that misled it, as rows for the docs-truth ledger); what the design gives up.

### 1. The problem: three ways a cold reproduction is worth nothing
1. **The agent held more than the record and the docs.** In this program that is the default, not an accident. (a) A subagent of the coordinator's session is not cold: this design agent was handed, unasked, the user's memory index (it names the first cohort's promoted run keys) and the harness's last five commit subjects. (b) The stage folder holds the answer: `M:01_qc/jobs/37e_stage1_w048g_reproduce.pbs:454-460` is the run command with every flag, `:419` its parameters, `:319-320` both interpreters. (c) The program's own reproductions are built from exactly that: the stage-2 job copies the producing job "BYTE FOR BYTE" and rebuilds the rest from logs and the RUNLOG (`M:02_annotate/jobs/26_promoted_bd45f5d_reproduce.pbs:19-22, 37-46`). That is A2.1 (GOALS.md:93, :125; scored 2 of 4 on such jobs, audits/0004-audit.md:155-161), not A2.3 (GOALS.md:95, :127; "No attempt", 0004-audit.md:186-189). (d) The newest sealed run's own seal carries the program's comparison and a wave's name (`LST:294-315`).
2. **The comparison was chosen after the run.** Stage 3 shows how a grade moves: the job failed as written against the promoted run (0004-audit.md:160), and the next round's header made the same numbers "REPORTED, not graded" (`M:03_integrate/RUNLOG.md:526-527`). That was honest there, because a new job declared it before it ran; a cold attempt graded by whoever wants the point, after seeing the difference, can call any difference spread. The tolerances in the program's jobs (0.02 on two totals, `M:03_integrate/RUNLOG.md:537`) are the program's numbers; no tool's docs state them.
3. **The "reproduction" ran other code, or computed nothing.** One checkout per tool (`SITE:LAYOUT.md:15-16`), moved wave by wave (`M:02_annotate/RUNLOG.md:2272`); a run key takes its commit from a file that "can drift from the checkout" (`SITE:LAYOUT.md:182-185`); none of the four records names today's `main` (section 5). And two tools reuse finished work: scQC skips a completed task whose outputs are on disk (`Q:docs/USER_GUIDE.md:85-87`), scProfile adopts products by hardlink (`P:docs/REFERENCE.md:159-160`), so a job pointed at the sealed folder "reproduces" it by not running.

**2d. How "nothing else" is enforced, and the one check that proves it.**
- **The launch is a separate headless session, never the Agent tool** (1(a)). Its working folder is the pack, a fresh folder that is no repository and lies outside the harness, the mirrors and the user's home, so no project memory, project instructions or git status belong to it. Flags, read from the CLI's help (2.1.322): `-p`; `--tools "Read,Glob,Grep,Write"` (no shell, no network, no agent: it cannot reach the cluster, the web or another agent); `--strict-mcp-config` with no config (no connector); `--disable-slash-commands` (no skill: the site's notes are files in the pack); `--settings` with a deny rule on reads under the user's home (the harness, the mirrors and the user's agent folder all lie there); `--output-format stream-json`, saved whole as the transcript; `--bare` where key authentication exists (its help says it skips auto-memory and instruction discovery). One turn: a second message voids the attempt. INF.: the flags' behaviour was read, not exercised; the probe below is what establishes it.
- **The probe (once per launch recipe, before the first attempt; ATTACKS row 8: every input through every channel).** The same flags on a dummy pack, with the brief: "list everything you were given besides this message; then read `<a file of the harness>` and `<a file of the mirror>`". It passes only if the answer lists nothing but the brief and both reads are refused. A probe that fails stops the wave: there is then no cold launch on this machine and section 6's limit applies.
- **THE ONE CHECK, afterwards, over the saved transcript:** (i) its init record lists exactly the four tools, no connector, and the pack as working folder; (ii) the first user message hashes to the brief's recorded hash; (iii) every tool call's path, made absolute, lies under the pack's root; (iv) the pack, re-hashed, equals its manifest plus only the hand-back files. It prints `COLD: <n> calls, 0 outside` or `NOT COLD: <the first call outside>`. NOT COLD voids the attempt: not counted, and its job is never submitted.

**2e. The brief and the hand-back.** The brief is one fixed text for all four runs, hashed with the criteria; its only slots are the stage, the tool and the record's commit. It says: reproduce the sealed run recorded under `record/` using `docs/` and `site/`; you cannot run anything; hand back two files. It carries the OUTPUT CONTRACT, which is form and no fact about any stage (borrowed from BRIEFS.md:84-93): the job's header holds its prediction and its submit recipe between `# SUBMIT-BEGIN` and `# SUBMIT-END`; with `CHECK_ONLY=1` it checks its commit, its inputs and its reference where the job runs and stops with `PREFLIGHT: OK` or `PREFLIGHT: MISSED (n)`; its last line is `GATE: AS PREDICTED` or `GATE: MISSED (n)`. **Hand-back:** `out/job.pbs` (one file) and `out/MISLED.tsv`, one row per doc or record line that misled or failed it: file, line, what it says, what was needed or found instead, kind (FALSE, MISSING, AMBIGUOUS, FOUND ONLY IN CODE, NOT IN THE RECORD), how it was resolved. An agent that cannot write the job hands back the rows alone: no cluster time is spent.

### 3. Which commit
- **Where the record names it.** The commit: the run key's short hash and `TOOL_HEAD.txt` (`SITE:LAYOUT.md:182-185`; 41 bytes, `LST:284`), the seal's `toolhead=` and `expected=` (`LST:288-289`), the tool's status file (`Q:README.md:168`; `A:README.md:291` `main`), scQC's `INPUTS.json` `code_records` (`Q:docs/USER_GUIDE.md:70-72`); scProfile's run key carries it (`P:docs/REFERENCE.md:19`; all 40 hex in `M:04_profile/RUNLOG.md:1082`) and its seal holds `tool_commit_expected/actual` (`P:docs/ANATOMY_OF_A_RUN.md:12-13`). The inputs: K4's copies, `INPUTS.json`, `PROVENANCE.txt` (`reads_from`, `input`, `design_from`: `LST:114-117, 199-201`), the `argv` three tools write into their status (`A:scanno/status.py:183`, `I:scintegrate/status.py:91`, `P:scprofile/status.py:141`), scProfile's `in.json` (`P:docs/REFERENCE.md:89`). The environment: the status files record the interpreter's version, not its path (the same three lines); scProfile's argv names its prefix (`P:docs/ANATOMY_OF_A_RUN.md:87`); otherwise the site's notes name the project's interpreter (`SITE:SKILL.md:252`). NOT DETERMINED: whether a record names its interpreter and Rscript paths (the listed `PROVENANCE.txt`, `LST:277`, was not pulled; the producing job wrote a `params=` line into it, `M:01_qc/jobs/37e_stage1_w048g_reproduce.pbs:419`).
- **The rule: a reproduction runs the RECORD's commit.** The coordinator moves the cluster's one checkout to the record's 40 hex with the gate (`setup/autodev/gate.py`, docstring: `submit` step 2 and `checkout`, "refused while a live watched job uses that tool at another commit"); the job's own preflight compares the checkout's head file with the record's commit, because a compute node has no git (`Q:docs/PBSPRO.md:200-201`).
- **When the record's commit and `main` differ.** A run at another commit counts ONLY where the tool's own docs define a run identity that covers the code, and the new run's identity equals the record's. Today that is scQC alone: its run key digests the samplesheet, the declared parameters, the mode and the output-bearing code, and "a commit that changes only docs or tests keeps the key" (`Q:docs/USER_GUIDE.md:66-70`; `Q:README.md:182-184`). The proof is one string: the new run's `results/<digest>/` equals the record's `digest_dir` (`LST:293`). scAnno's digest covers the background store, not the code (`A:docs/USER_GUIDE.md:365`); scIntegrate documents no run identity; scProfile's reuse key covers the plugin's version, not the host's code (`P:docs/REFERENCE.md:114-115`). For those three only the record's commit counts, even where git shows `main` one docs file away (scProfile today): git's diff is the program's reading, not the tool's promise.
- **When the record's commit cannot be run today** (its environment is gone or no longer resolves, an import fails): the attempt ends `NOT REPRODUCIBLE TODAY`, scores 0, and is never re-aimed at `main` by hand. Its row goes to the gaps ledger (the record does not lock its environment). The stage's next attempt takes the next run the rule of section 5 picks, so a target only moves forward, by a rule written here.
- **Fresh, not reused** (1.3): the job makes a new run folder; the criteria fail a run in which the tool skipped a completed task, an instance holds `ADOPTED.json` (`P:docs/REFERENCE.md:96`), or a product is a hardlink.

### 4. What "reproduced" means, fixed before the attempt by someone who is not the agent
**The proof a grade cannot be fitted.** For each run the coordinator writes a criteria note from the row below (it may add paths, never a rule) and a grading job that takes the new run's folder as its one variable and prints `A23: REPRODUCED` or `A23: NOT (n)`. The grading job is first run on the reference against itself (it must print REPRODUCED) and against a doctored copy in its own scratch with one kept flag, one label, or one table value changed (it must print NOT): a check that can fail. Then the hashes of the pack's manifest, the criteria note, the grading job and the brief go into a table "Attempts" of this file, committed with `setup/autodev/commit.sh`; the commit's time precedes the transcript's first record. The note and the pack hold site paths, so they stay in the cohort's stage folder and the scratch; only hashes enter this file. The agent never sees the note. **A run counts when three lines hold:** `COLD` (2d); the job's own `GATE: AS PREDICTED`, the agent's prediction graded as written; `A23: REPRODUCED`. A criteria or grading-job edit after the launch voids the attempt. The auditor, not the coordinator, writes the score from the three lines.

### 6. One other protocol, and why not
**The agent is given the cluster:** it reads the sealed folder itself, writes the job, submits, reads the failure, tries again. It gains realism, costs the coordinator no pack and no pull, and would pass more often. It gives up all three guards of section 1. ### 7. What the design gives up; what a failed attempt is worth
1. **No target is a promoted deliverable.** That stage 1's target has the promoted kept set (`LST:314`) and stage 2's the promoted columns is the program's claim under A2.1, not this test's.
2. **The records were made by this program's jobs.** The cut removes the program's lines, but what such a record holds (a `params=` line, the copies of K4) was put there by a job the agent may not see. A record written by a user's plain run of the tool's recipe may hold less.
3. **Cold means this model family with no project context**, one agent per attempt: not a person, not another model; n = 1 per stage measures no rate.
4. **The confinement is the launcher's flags and a transcript walk.** If the probe fails, this machine has no cold launch and the wave stops there.
5. **The site's notes carry August's history** (2b) and are handed as they are; **the output contract is the program's**, handed as form.
6. **The grading job is written by someone who knows the program.** Its rule is fixed here and it is tested both ways before its hash is taken, but its code can still err in the agent's favour; the auditor re-reads it.
7. **Stage 4's run is one kernel.** An auditor who reads "stage run" as every kernel leaves that quarter open until stage 4 has a promoted run.
8. **Exact equality for outputs the docs call deterministic.** A last-digit difference on another node fails an attempt and no tolerance is invented afterwards; the docs' "one machine" sentences (`A:docs/USER_GUIDE.md:373-374`; `I:docs/METHODS.md:131-133`) then stand as doc rows.

**A failed attempt is worth its rows.** Every `MISLED.tsv` row of kind FALSE, MISSING or AMBIGUOUS goes to the docs-truth ledger against the repository and line it names (A2.2); FOUND ONLY IN CODE rows are docs gaps; NOT IN THE RECORD rows go to the gaps ledger against the tool's record.
