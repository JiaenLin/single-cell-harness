# W069 (PLAT): the lab's .rds reader loses an object's last slots on a function kept in `commands`

**Registered** 2026-11-14 by the coordinator, on the PI's bug report of that day ("A BUG WHEN I UPLOAD C46_org.rds to
scrnaseq-lab": the page said "That file did not open. this .rds does not hold an S4 object, so it is not a Seurat
object."), while the program is PAUSED (D-056): this one bug is the PI's own request; nothing else is resumed.
**Repository** scrnaseq-lab, branch `fix/rds-namespace-layout`, from `main` (`537cfaa`). **Goals** PLAT.2, A6.2.
**Gap** GAP-C141.

## What was measured before any code (the coordinator; the live lab's own reader run by Node on the PI's file)
- The file is a gzip, XDR, serialization version 3 .rds written by R 4.4.0 whose top item IS an S4 object (type 25,
  the object bit set, attributes present): the page's sentence is false for it.
- The reader returns the object with 13 attributes: the 12 slots up to `commands`, then `names`; no `tools`, no
  `class`. `commands` holds 9 items and NO names; the stray `names` holds the 9 command names. So the reader came out
  of `commands` ONE ITEM SHORT, took the list's own names for the object's next slot and stopped, leaving `tools` and
  `class` unread, and nothing noticed that bytes were left.
- The item it miscounts (a trace of every item walked): a function kept as a parameter of one command, whose
  environment is a package namespace. R writes a namespace, a package environment and a persistent name as a BARE
  string vector (an integer 0, a count, then that many strings: `OutStringVec` / `InStringVec` in R's
  `serialize.c`, read at R's trunk); the reader reads ONE ordinary item there. With a count of 2 the bytes still
  line up, so nothing fails where it happens: the function's body is left unread and every enclosing list is one
  item short from there on.

## THE CLASS
The reader's layout of an item type differs from the layout R's own reader uses, and a miscount that still ends on
an item boundary is returned as a shorter object with no error: a false statement about the user's file follows.

## THE SIZE (three changes, the lab only)
1. `src/lib/rds.ts`, every item type read against R's `ReadItem`, and each difference closed: the three bare string
   vectors (namespace, package environment, persistent name); a weak reference (R reads nothing after its flags; the
   reader read two items); attributes after byte code and after a single string when their flag is set (R reads
   them; the reader did not); a builtin or special function (a length and a name; the reader refused the file).
2. `read()` ends where the stream ends, or it throws: a reader that finished the object with bytes left has lost its
   place and says so as its own fault, never returning the shorter object (`GzWindow` and `Bytes` say whether a byte
   is left).
3. `src/lib/seurat.ts`: "does not hold an S4 object" is said only of a value that is not one; and the tests: each
   layout written as R writes it (failing on `main`), a real object written by R with a namespace function, a
   builtin and a package environment among a command's parameters, and leftover bytes refused.

## Acceptance check
- The PI's file scans: class Seurat, its matrices and embeddings listed; on `main` it fails with the page's sentence.
- Each new test fails on `main` and passes at the head; the suite, lint and build as before plus the new tests.
- A proof table; an independent check (not the builder) before the deploy (D-045).

No score moves. The live lab opens Seurat objects whose commands keep a function from a package (any object where a
function was passed as an argument to a logged Seurat command), which today it refuses with a false sentence.
